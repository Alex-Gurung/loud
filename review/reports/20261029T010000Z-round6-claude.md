# Round 6: the round-5 fixes and what was added since d99a223, research and code lenses (Claude)

**Verdict.** Most round-5 fixes hold. The E4 clock, `direction_stats`' matrices, E9's norm, E10's `agree_over`, the batch guards, the non-finite stops and Turns' two-way failure all check out, and the eight requested CPU checks plus 76 pytest tests pass. The round-5 blocker is not fixed on the torch the GPUs run, though. Torch 2.13 (the pod image) keeps Dynamo config overrides per thread, so Turns' second part runs with the default recompile limit of 8. It hits that limit at its first new shape, and the code object then stops compiling on every thread. Every queued Cut job would compile 9 of its `chain_chunk` graphs and run the rest eagerly: part 1's chain, all of E11's runway probes, and every E7 row count after the first. The warmup check cannot notice. Separately, E6's plots crash as soon as a Cut cell finishes.

### 1. [blocker] On torch 2.13 the Turns pool thread runs with Dynamo's default recompile limit (8). Once it hits that limit, `chain_chunk` stops compiling everywhere, and the warmup check passes anyway.
- where: `loud/cut.py:79,84` (parts 1.. run on a `ThreadPoolExecutor`), `loud/cut.py:454-455,737-746` (the limit raised on the main thread only), `loud/cut.py:677-695` (warmup check), README:347-349 ("Every shape the run will use compiles in the warmup ... fails the job if the warmup reaches it"); torch 2.13 `torch/utils/_config_module.py:53` ("User overrides are thread-local", ContextVar-backed) and `torch/_dynamo/convert_frame.py:2037` (a limit hit sets the code's strategy to `RUN_ONLY`)
- evidence:
  - **Per-thread config.** `torch._dynamo.config.recompile_limit = 128` on the main thread, then read from a `ThreadPoolExecutor` thread. Torch 2.10 (CPU venv) gives 128; torch 2.13.0 (`/tmp/.venv` on this machine, the image's version) gives 8.
  - **Run-only spreads to the main thread.** A `dynamic=False` function was compiled for 9 `site` values on the main thread. A new site on the pool thread then compiled nothing on 2.13, and after that a new site on the main thread compiled nothing either: 9, 9, 9 entries. On 2.10 the counts were 9, 10, 11 (`scratch/exp/runonly.py`).
  - **The port itself, Dynamo on.** `scratch/exp/dynamo_plan.py` runs `loud.cut.run` with Dynamo enabled. The backend is eager, so guards and caching are real but nothing goes to Inductor. `chain_tokens` is 16, so each sequence has 4 token chunks.
    - Variants case (E7 tiled 64 rows, self-check, E11, E8; 2 virtual GPUs per sequence). Torch 2.10: `chain_chunk: 14 graphs compiled; 14 expected, limit 64`, with no compile after the warmup. Torch 2.13: `hit config.recompile_limit (8)`, then `12 graphs compiled; 14 expected, limit 64`, and the job carries on.
    - 7m E7 ramp (64 rows to the full cycle, drift check). Torch 2.10: 36 of 36. Torch 2.13: `8 graphs compiled; 36 expected, limit 72`.
    - With `contextvars.copy_context().run` in `Turns.run`, torch 2.13 gives 14 of 14.
  - **On the 38m model.** Part 0 compiles its 9 graphs (embedding plus 8 mid sites) before part 1 reaches the chain, so part 1's first new shape hits the limit (9 ≥ 8). That leaves, for the whole run:
    - `e6.cut_k1`, E6, E11 and `verify.cut_prefix`: part 1's 8 mid-site graphs eager on every Cut update; E11's 16 runway graphs eager too.
    - E7: 9 of its 136 graphs compiled.
  - **What it biases.** E7's "equal loss at lower time" against `e6.cut_k1` is biased in the same direction as round 5, now worse. Every Cut wall-clock (E1's 1M number) is inflated. The cost per eager update is unverified on a GPU; round 5 estimated +20-40% for an eager chain.
  - **Why nothing catches it.**
    - The warmup fails only if `compiled >= recompile_limit`, and that limit is twice the plan.
    - `fail_on_recompile_limit_hit` is set only when the debug API is missing, and it would be thread-local too.
    - `cut_compile_plan`'s `assert len(plan.graphs) < plan.recompile_limit` (`tests/method_checks.py:1157`) is true by construction.
    - All CPU checks run torch 2.10 with Dynamo disabled.
  - **Scope.** All 45 queued Cut jobs (snapshot `f99eeabb`) carry this code.
- fix:
  - In `Turns.run`, submit `contextvars.copy_context().run, self._part, p, job`, so each part sees the caller's Dynamo and Inductor overrides.
  - In `warmup`, fail unless `compiled == len(self.graphs)`. Record the count again in `result.json` at the end, and fail if it grew in the timed loop.
  - Add a CPU check that runs the port with Dynamo on (backend `eager`) under torch 2.13. Mine takes about 2 minutes.
  - Resubmit the Cut jobs.

### 3. [minor] E7's control variate has coefficient 1, so it beats the plain estimate only when the guess's norm is roughly right, and the precondition gate checks cosine only
- where: `loud/cut.py:300,318-322`; README:354-358 ("a variance that shrinks with the guess's error"); `configs/e7/precondition.yaml`; `loud/diagnostics.py:186-187` (credit_dump reports cosine quantiles only)
- evidence: over the basis' random signs, a token's R-row estimate has variance (W/R − 1)·‖g‖² when plain and (W/R − 1)·‖g − guess‖² with the guess. The guess helps only if ‖g − guess‖ < ‖g‖. With cosine c and norm ratio ρ = ‖guess‖/‖g‖, that means ρ < 2c: 1.8 at c = 0.9 and 1.4 at c = 0.7. For example, a guess at cosine 0.95 with twice the norm has 1.2× the plain estimate's variance. The identity path's guess carries the top credit down the residual scalars and ignores the blocks' Jacobians, and nothing measures its norm. A "good cosine" gate can therefore pass while every E7 ramp is noisier than plain sub-sampling. E7 would then fail for a reason that has nothing to do with its premise. Unverified: no early checkpoint exists to measure ρ on.
- fix: add per-token ‖g − guess‖/‖g‖ quantiles (and ρ) to `credit_dump`, which already saves both tensors, and add them to the gate. Alternatively, scale the guess per site by a fitted coefficient.

### 4. [minor] The E7 gate's "median over the nine sites" includes the embedding, which E7 does not guess
- where: `configs/e7/precondition.yaml` (comment and values), `loud/gate.py:24-27`; `loud/diagnostics.py:169-175` (credit_dump's embedding "guess" is the identity path's measured RMS-norm cycle); `loud/cut.py:217-224`, README:358-359 (E7's guess acts only at the 8 mid sites)
- evidence: the gate takes `statistics.median` over every site in `credit_dump.json`, `emb` included. That value comes from a measurement, so its cosine is likely high. It makes "above 0.9 at 20%" easier and "below 0.7 at 100%" harder, and neither describes the guess E7 actually uses.
- fix: give the gate a site filter (for example a fourth element `mid`), or skip `emb`.

### 5. [minor] `direction_stats`' pending update leaves out the current gradient's update of the rails, so the batch gradient gets about half its weight
- where: `loud/diagnostics.py:274-280`; `loud/checkpoints.py:56-62`; compare boost-cut `noise/train/boostcut/run.py:972-974`
- evidence:
  - ANVIL II first lerps `fast` and `slow` toward g, then forms `g.lerp(w·fast + (1−w)·slow, beta)`. `direction_stats` lerps g toward the rails saved after the previous step.
  - At beta = fast_beta = 0.93, ANVIL's pending update is 0.135·g + 0.865·fast, and `direction_stats`' is 0.07·g + 0.93·fast.
  - `.optim.pt` saves neither `fast_beta` nor `slow_beta`, so the step cannot be rebuilt exactly. The top-16 directions, which E8's knob centre is read from, shift towards the momentum.
- fix: save `fast_beta` (beta when not engaged) and `slow_beta`, and in `direction_stats` lerp the rails with g before forming the pending update.

### 6. [minor] E8's Cut control runs PR #40's compiled ANVIL II and the damped cell runs an eager copy, so the pair differs by more than the damping; "to the bit" holds only eager against eager
- where: `loud/cut.py:477-484`; `loud/anvil.py:77-92`; PR #40 `run.py:2077` (`@torch.compile(dynamic=False) def anvil_update`); README:32,377; `tests/method_checks.py:1036` (both sides eager, Dynamo disabled)
