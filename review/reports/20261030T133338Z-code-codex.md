### 1. [major] H8 projects key credit on the wrong side of RMSNorm
- where: `loud/h8.py:130`, `loud/h8.py:157`
- evidence: `cut_forward` passes `m.norm(x)` into attention, where `ReadCredit` projects its incoming credit. The reference’s `key_input_credits` probes `capture.blocks[i]`, before that norm. Writing the projection as P and the norm’s pullback as J, H8 computes J(Pg), whereas input probes estimate P(Jg). These differ: a deterministic CPU example with width 128, 32 Hadamard rows and seed 4 produced **9.35% relative error**. `h8_knobs` checks full-basis identity and isolated projection arithmetic; neither catches this placement error.
- fix: apply `ReadCredit` to the unnormalized input on the key branch, then normalize it. Add a partial-row comparison against probes before normalization.

### 2. [major] Pending baselines crash E19 and E20 board generation
- where: `loud/board.py:240`, `loud/board.py:247`
- evidence: E19 checks whether its target exists but subtracts its `val_mean` without checking for `None`. E20 similarly subtracts `by_key[SYNTH]['val_mean']` unchecked. Direct calls with completed experimental arms and pending baselines both raised `TypeError: unsupported operand type(s) for -: 'float' and 'NoneType'`. Missing E20 baseline entries also raise `KeyError`.
- fix: require the relevant baseline and a non-null validation mean before computing differences; otherwise return `waiting`.

### 3. [major] E20 can pass while its stated batch-16 criterion fails
- where: `loud/board.py:252`
- evidence: the experiment specifies batch 16’s partial-row cost against the `0.02` bar, but the verdict uses `min` across batches 8 and 16. Supplying costs of `+0.010` at batch 8 and `+0.050` at batch 16 returned `met`. It can also declare success before batch 16 finishes.
- fix: base the verdict on the completed batch-16 pair; retain batch 8 as supporting information.

### 4. [minor] Every deep-readout solve synchronizes CUDA with the CPU
- where: `loud/cut.py:231`
- evidence: the installed `torch.linalg.solve` documentation explicitly states that CUDA inputs synchronize the device with the CPU. `deep_pass` invokes it separately for seven later sites per token chunk: **112 synchronizations per normal update** with four 2,048-token sequences and 512-token chunks. Runtime impact remains unmeasured because CUDA was unavailable.
- fix: use `torch.linalg.solve_ex(check_errors=False)` and aggregate solver-status checks once per update.
