# Round 5 review: proxy experiments (E2, E3, E4, E8, E9, E10, E12 proxy), research and code lenses (Claude)

Verdict: the proxy-experiment code mostly does what the plan asks, and its CPU checks are real. All 11 method checks named in the brief pass, and so do the 52 tests in `test_variants.py` and `test_harness.py`. The E4 undo is exact for both ANVIL II implementations, the E2, E10 and E9 arithmetic is right, and E3's split and schedule are correct. Three problems need fixing before these cells run:
- E8's diagnostic falls back to gradient directions on every real checkpoint, which undoes a ledger item marked fixed.
- E4's undo also rewinds ANVIL II's schedule clock, so the momentum schedule the README says "stays" is stretched by the acceptance rate.
- E12's summary table tells readers the backprop proxies have no end merge, but this commit gave them one.

### 1. [major] `direction_stats` (E8's diagnostic) never uses the pending update on a real checkpoint; round-3 ledger item #2 is not fixed
- where: `loud/diagnostics.py:258`, `loud/diagnostics.py:272`; `loud/checkpoints.py:57-59`; `tests/method_checks.py:296-301`; `configs/h6/direction_stats_c20.yaml:1-2`
- evidence: `names` takes every 2-D `transformer.h.*` weight, which includes the four `attn.ve_gate.weight` matrices. `checkpoint_optimizer` saves ANVIL II's state only, and ANVIL II excludes `ve_gate`. So `all(n in state ... for n in names)` is always False, and `source` stays `'gradient'`. I ran a 2m-preset proxy run with `checkpoints: true, checkpoint_optimizer: true` (scratch `scripts/ds_a.py`), then called `direction_stats` on its `ckpt_50.pt` and `.optim.pt` the way `run_task` does (`scripts/ds_b.py`). It printed `directions_from: gradient`. The method check passes only because its fake state is built from all of `stats`' names, `ve_gate` included. The queued `e1.bp_b4.s0` and `h6.direction_stats_c{20,100}.s0` both run snapshot `1b32cb36`, which has the same code, so E8's h²/c table and the choice of E8's knob centre would describe gradient directions. The h6 config's own comment says "batch gradient", which contradicts the docstring and the ledger.
- fix: build `names` with `anvil.is_anvil_matrix` (skip `ve_gate`), or decide per matrix. Rewrite the check to load a state saved by `FractionCheckpoints.save`, not a fake one. Resubmit `configs/h6/direction_stats_*` and fix their comment.

### 2. [major] A rejected E4 step rewinds ANVIL II's clock, so its momentum schedule follows accepted updates while the warmdown follows batches; the README says the schedule "stays"
- where: `loud/variants.py:109`, `loud/variants.py:117-119`; `README.md:249-252`
- evidence: `restore()` sets `o.t` back to its saved value. `rail_beta()` and `engaged = t >= engage` read `t`, but `set_rate` uses the loop step. At batch 8 (606 updates) ANVIL's warmup is 122 updates, engage is at 261 and the cooldown runs after t = 581. The plan's factors settle at 82% acceptance (adapt): t reaches about 497 by the last update, so the beta cooldown never happens and engage moves to about update 318. At adapt_t60's 60%, t ends near 364 and engage moves to about update 435. That is a second change inside each adapt cell, including the `_nowd` cells, which are E4's point and for which the README says "ANVIL II's own momentum schedule stays". E3 ties the clock to the single run's update number instead (`loud/population.py:210`).
- fix: after `restore()`, set ANVIL II's `t` to the loop step (`step`), as E3 does. Keep restoring the rails, energy and Adam state. Or, at the least, log `t` and correct the README.

### 3. [major] E12's summary says the backprop proxies have no end merge, but `bp_pr40` and `bp_pr46` now run one; the README never mentions the proxy's `end_merge`
- where: `loud/plots.py:299-300`; `configs/e12/bp_pr40.yaml:3-4`, `configs/e12/bp_pr46.yaml:3-4`; README Methods (only the Cut chain's end merge is described)
- evidence: `e12_table` appends "the backprop proxies (bp_*) have no merge, so compare them with the plain column". d99a223 added `end_merge: true` to both bp configs, so their `val_loss` is after the merge and `val_loss_plain` exists. A reader following the note would compare a merged proxy with the record's plain weights, which is the wrong pairing for E12's question (backprop with the record's optimizer and schedule as a fair baseline against the record). `git log` shows the note came from round-4 fix #10 (5925450), before the merge commit.
- fix: drop the note, or say that both sides report merged (val) and plain (val, plain weights) and should be compared column by column. Add the proxy's `end_merge` option (recipes pr40/pr46) and E12's bp cells to the README.

### 4. [minor] E3's held-out curve and the results table's `heldout_min` read midpoint scores, not any copy's
- where: `loud/plots.py:110-112`; `loud/collect.py:52`
- evidence: population runs log the copies, the six midpoints, the ensemble mean and the final score to `heldout.jsonl` at the same step. `curves_plot` keeps one value per step and drops only `mean_decay`, so the last entry wins: the `2-3` midpoint at every checkpoint. I checked this on the CPU `population_run` outputs (select and ensemble). `heldout_min` takes the minimum over all of them. For `select` it came out at 7.3304, a midpoint, while the best copy ever scored 7.3441 (the final weights, also 7.3441). If midpoints beat their copies, which is likely, E3's `heldout_min` is biased low against `e1.bp_b4`'s.
- fix: skip entries with `copy`, `midpoint` or `mean` in both readers. Plot the per-copy curves separately.

### 5. [minor] E9 rescales R @ pending to √min(rows, cols), which is up to 1.3× the norm `polar()` actually gives
- where: `loud/fisher.py:77`; docstring `loud/fisher.py:8` ("so its rates keep their meaning"); `README.md:296`
- evidence: the six quintic maps send a normalised singular value below about 3e-3 to less than 1 (9.1e-4 maps to 0.54; scratch `scripts/polar_norm.py`). On the record checkpoint, with the gradient of 2 held-out sequences of 1,024 tokens, ‖polar(g)‖_F / √min had these medians per matrix type: c_q 0.91, c_k 0.90, c_v 0.81 (range 0.77-0.82), attn c_proj 0.89, c_fc 1.00, mlp c_proj 1.00. So E9's steps on c_v run about 1.23× ANVIL II's at the same rate, and attention's about 1.1×. The size of the step is confounded with the preconditioner against a 0.02 success margin. The pending update mixes in momentum and is probably closer to 1, but nothing measures it.
- fix: scale to `polar(pending).norm()` (one extra polar per matrix per step; E9 is not timed for speed). At the least, log the ratio.

### 7. [minor] E8's sub-options are accepted with E8 off

### 8. [minor] No GPU smoke run gates E2, E4 or E10 (32 jobs), although E3, E8 and E9 each have one
- where: `configs/verify/` (only `population_smoke`, `curvature_smoke`, `fisher_smoke`); `configs/e2/*`, `e4/*`, `e10/*` wait only on the bp_b8 gates
- evidence: the CPU checks never reach the CUDA-only parts of these paths:
  - E10's tensor hooks run on the autograd device thread and use TF32 sign matmuls;
  - E4's `_foreach_copy_` and `_foreach_zero_` mix CUDA tensors with Adam's CPU `step` tensors;
  - E2's bf16 displacements are on the GPU only.

  The README's cost figures (2.3×, 1.35×, 1.1×, 2×) are unmeasured. A crash in the warmup costs little, but a slowdown or a mid-run failure would hit every seed.
- fix: one short 1M smoke run per path (blur, adapt, cap, agree), like `curvature_smoke`, as an `after` for its experiment. It also measures the step time.

## Checked and fine
- **Test runs:** `method_checks.py` passes `variants_blur`, `variants_control`, `variants_control_pr40`, `variants_shaping`, `variants_run`, `anvil_hook`, `curvature_damping`, `fisher_factor`, `population_rules`, `population_run` and `proxy_merge`. `pytest tests/test_variants.py tests/test_harness.py` gives 52 passed.
- **E2 Blur:**
  - |r| = τ · 0.01 · RMS · √512 equals PR #40's chain probe: a ±1 Hadamard row (unnormalised, `hadamard()` at `archive/10M/train/val/run.py:178`) times `chain_sigma` times each token's RMS (`:1311`).
  - The sites are the raw `wte` output (PR #40's `e`) and the attention output added to the block input.
  - The same r is used for + and −. `train_loss` is the clean no-grad loss, the gradient is the mean over 2 × micro-batches, and the generator is separate and reset with the trainer.
- **E4 Snapshot:**
  - Restores the weights, every state tensor and both clocks. With PR #40's and PR #46's `BatchedAnvil` the per-parameter `fast`, `slow` and `energy` are views into the stacks, so copying back into them restores the stacks.
  - Zeroing first-step state equals a fresh optimizer, including for the stacks.
  - The multiplier is applied after `set_rate` and logged as the effective `lr`. Each update uses one fixed set of micro-batches for the gradient and the trial loss.
  - 0.9294 for 60% acceptance and 82% for 1.05/0.8 are both right.
- **E10:**
  - cap takes the quantile over all B · T tokens per layer, keeps bf16 credits and inputs (about 0.32 GB per sequence), and `torch.quantile` stays well under its size limit at batch 8.
  - agree's counts are exact (±1/0 in TF32 with float32 sums).
  - Linear weights skip autograd's weight gradient, so nothing is counted twice, and `per_sequence_grads` is correctly blocked.
- **E3:**
  - The split: prefix 242, rest 3,880, copy c takes `rest[c::4]` for 242 rounds, 8 sequences unused, each used once.
  - `global_step` sets the warmdown, and ANVIL II's `t = step - 1` follows the single run (the run ends at 1,210 of 1,212).
  - The rules match the plan: average keeps each copy's optimizer state; select copies state without aliasing (`deepcopy`, and the group pointers are fixed); ensemble keeps the mean only if H3 prefers it.
  - barrier = midpoint − worse end. `select` scores are timed and monitoring is paused. The prefix is `e1.bp_b4`'s trajectory.
- **E8 CurvatureDamping:**
  - λ = `curvature_damping` · anvil_lr² · max(1, rows/cols) matches ANVIL II's step along a unit direction. The config's "about 470 / (h²/c)" for B = 4 checks out (1 / (4 · 0.023²) = 472).
  - h and c are on the same mean-loss scale. h²/c is scale-free, so it is comparable with `direction_stats`' summed-loss values.
  - The noise is a within-update variance averaged since the refresh. The refresh order is right: old factors on the refresh update, then new directions.
  - The float32 copy does not carry grads. The warmup's update 1 is a refresh, so the float32 flex attention compiles untimed.
  - The 1,536-pass count and roughly 20 minutes per run are consistent.
  - `damp()` scales exactly the tracked components. The README flags the after-`polar()` default and gives its reason.
- **E9:** the sampled labels come from the soft-capped softmax on the same graph. d is taken with respect to each block matrix's output (K-FAC's G factor over positions), `inverse_root` is correct, damping is relative to the mean eigenvalue, the scale of S does not matter, and the training gradient is unchanged (checked).
- **ShapedAnvil:** line for line, `Anvil.step` with one substitution. E8 and E9 are blocked for recipes other than boostcut.
- **Proxy end merge:** it calls the record module's own `end_merge` (identical in PR #40 and PR #46, with the same MERGE constants). The means follow PR #40's rule (`begin/len ≥ 0.6`, every 5 and the last update, float32). The plain weights are saved untimed, the merge is timed, and `val_loss_plain` is scored in a fresh process. With `boost_batch = cut_batch = 4`, PR #46's two-phase schedule is one continuous schedule, as the proxy runs it.
- **Configs:** E2, E4 and E10 are `e1.bp_b8`'s args plus one variant. E3, E8 and E9 match `e1.bp_b4` in everything that affects training. Seeds are 0-2 except the plan's single `_nowd` runs. Held-out is 32 everywhere. The smoke configs' update and refresh counts are as their comments say.
- **One change per variant:** `options.py` blocks any two of the five variant switches. `warmdown` and `lr_mult` stay free, as E4's `_nowd` cells need.
- **Plots:** E4 (acceptance per 50 updates, effective ANVIL II rate against `e1.bp_b8`), E2 (the gap table), E8 (the damping table and the h²/c figure) and the baselines (bp_b8 for E2, E4 and E10; bp_b4 for E3, E8 and E9) read the files the plan names.
