### 1. [major] The worker tests use `LOUD_QUEUE_DIR` from the environment, so they can claim and fail real queued jobs
- where: `tests/test_worker.py:13-14`
- evidence: `env_for` sets `LOUD_ARTIFACTS` but passes `LOUD_QUEUE_DIR` through from `os.environ`. `paths.QUEUE` gives that variable precedence, and the GPU pods export it (`worker/gpu_worker.yaml:52-53`, `worker/launch_worker.sh:7`). To show it, I put a decoy job `e1.bp_b8.s0` (priority 50) in `scratch/fakeq` and ran `LOUD_QUEUE_DIR=scratch/fakeq pytest tests/test_worker.py`:
  - the test's worker claimed the decoy first and moved it to `failed/` (`code snapshot check failed: ... /nonexistent/MANIFEST.json`);
  - the test jobs landed in `fakeq`, and the test failed.
  Pointed at the live queue, this would use up attempts on real jobs or fail them.
- fix: in `env_for`, also set `LOUD_QUEUE_DIR=str(tmp_path/'artifacts'/'queue')` (and `LOUD_DATA`).

### 2. [major] Resubmitting a queued job ignores changes to `after` and `priority` and reports `unchanged`
- where: `loud/jobqueue.py:101-110`, `loud/run.py:53-54`
- evidence: `config_hash` leaves out `after` and `priority`. For a queued job with the same hash, `submit` returns `unchanged`, or updates only the `code_*` fields. Test in scratch:
  - queued `t.b` (priority 50, no `after`);
  - edited the YAML to `priority: 1, after: [t.a.s0]` and resubmitted, then resubmitted again with `--priority 0`: both printed `unchanged t.b.s0`;
  - the record still says `after [] priority 50`.
  Adding a verification gate to an already-queued E-cell therefore does nothing, and the `--priority` override is a no-op for existing jobs.
- fix: on a same-hash resubmission of a queued job, refresh `after`, `priority`, `config_path` and `spec.notes`, and report `updated` when any of them changed. The live tree's `SCHEDULING` tuple appears to do this; it needs a test.

### 3. [major] The git provenance in every `config.json` and in the results table is false

### 4. [major] The H2 `b_simple` estimator can never exceed the batch size (about 8)
- where: `loud/pergrad.py:56-61` (docstring at 4-6)
- evidence: `mean_sq = |ḡ|²`, and its expected value is `|G|² + tr(Σ)/B`. So the logged value is `≈ B·B_true/(B + B_true) < B`. I drove `PerSequenceGrads` with synthetic gradients (`scratch/bin/bsimple.py`, B=8, 20 trials each):

  | true B_simple | logged b_simple |
  | --- | --- |
  | 1 | 0.89 |
  | 8 | 4.01 |
  | 100 | 7.41 |
  | 1000 | 7.93 |
  | 1e5 | 8.01 |

  The docstring calls this McCandlish's B_simple, and it is "the quantity E8's direction statistics refine".
- fix: use the unbiased `|G|² ≈ |ḡ|² − tr(Σ̂)/B` (McCandlish App. A), and log both terms.

### 7. [minor] `loud.refs --check` passes when the data is missing, and the bootstrap relies on it
- where: `loud/refs.py:84-90`, `scripts/prepare_data.sh:13`, `worker/launch_worker.sh:43`
- evidence:
  - With `LOUD_DATA` set to an empty dir, `--check` prints `"train.pt": "missing"` (likewise `val.pt` and `test.pt`) and exits 0. A pod with a bad mount passes "fail fast" and then fails every queued job; failed jobs are not retried.

### 8. [minor] The float32 gradient accumulation launches about 650 extra kernels per update on the GPU path
- where: `loud/proxy.py:97-115`
- evidence: the model has 60 parameter tensors, only 5 of them bf16 (`wte`, `value_embeds`). With micro_batch 1 and batch 8, each update runs:
  - 60 `zero_` calls;
  - 8 × (60 `add_` + 5 `.float()` copies);
  - 60 divides.
  That is about 650 launches, roughly 3–5 ms of host time per update; I could not time it here. It is a few percent if the loop is launch-bound.
- fix: let autograd accumulate in place for the float32 parameters (same sequential fp32 sums, bit-identical) and keep accumulators only for the 5 bf16 tensors, or use `torch._foreach_add_`.

## Checked and fine
- **Data order and held-out split:** `randperm(N, seed 1)`, the last 32 sequences of the order held out, and the 10M slice hash all match `backprop_preset.py` and PR #40's `train_stages`.
- **Gradient averaging and objective:** `Trainer.gradient` matches `backprop_preset.step_fn`:
  - per-sequence batch-mean loss;
  - float32 mean, then cast to each parameter's dtype;
  - zero gradients for parameters that got none;
  - `requires_grad_` toggled around the batch;
  - loss averaged over micro-batches.
  `micro_batch: 8` reproduces the one-process script's warmup noise and gradient exactly.
- **Schedule:** `set_rate` equals backprop_preset's `min(1, left/warmdown)` at `final=0` and is PR #40's `set_rate` verbatim.
- **Warmup and init:** warmup is followed by a fresh model and optimizer; `make_model` reseeds the RNG.
- **ANVIL beta logging:** `rail_beta()` has no side effects.
- **Timing:** one sync per step plus excluded diagnostics, as in the reference; `.item()` adds no extra sync.
- **Trajectory means:** match PR #40 (first sequence ≥ 0.6, every 5 updates and at the stop step, same decays, first observation copies).
- **Scoring:** official val via `utils/eval.py` in a fresh process from the job's snapshot, strict load; the test loop mirrors `evaluate()`.
- **Queue:** priority ordering, dependency waiting and blocking on a failed check, lease expiry with the run moved aside, release, last-attempt failure; JSON writes are atomic (`.writing-` temp files are not globbed). The 12 tests pass in 35 s.
- **Worker shutdown:** SIGTERM kills the child process group, waits 60 s, then releases the job. The worker is PID 1 (via `exec`) and the grace period is 120 s.
- **Snapshots and pins:** content-addressed snapshots with a safe rename race; the guard against loading two reference trainers in one process; the fixed-model hash check after import.
- **Locking:** `/mnt/disk` is a kernel CephFS mount (type `ceph`), whose client supports cluster-wide `flock`. I did not test this across several clients.
