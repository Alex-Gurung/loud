# Round 5, Cut-chain port (`loud/cut.py`): research and code lenses (Claude)

**Verdict.** The 8-GPU emulation is faithful. Virtual ranks, seeds, roles, the Turns baton, the step's sum and division, the phase switch and the end merge all match `train_stages`, and the three CPU checks pass (`cut_ranks` bit for bit). E6's windows are exact as well: I also checked split = 2 numerically. One problem invalidates E7, though. The record caps Dynamo at 64 graphs per function, and with the ramp's row counts `chain_chunk` exceeds that cap during the warmup. Most E7 Cut updates, every full-cycle one among them, then run eagerly, which biases the experiment's "equal loss at lower time" test against E7. No config pins the GPU type, and E7's baseline lives in another experiment, so the results table cannot flag a GPU mismatch either.

### 1. [blocker] E7's ramps (and `cut_smoke`) exceed the record's Dynamo limit of 64, so most of their Cut updates run `chain_chunk` eagerly, every full-cycle one among them
- where: `loud/cut.py:410` (warmup), `loud/cut.py:27-29` and README ("Every shape the run will use compiles in the warmup"); `external/noise/archive/10M/train/val/run.py:55` (`cache_size_limit = 64`), `:606` (`chain_chunk = torch.compile(..., dynamic=False)`)
- evidence:
  - **Graphs per row count.** `chain_chunk` takes `site` as a Python int: the code branches on it, so Dynamo builds one graph per site value. It also takes `move` of shape `[512, P(+4), 512]`. Each chain row count therefore needs 17 graphs: part 0 at site −1 (P), part 0 at sites 0–7 (P + 4, the scalar probes), and part 1 at sites 0–7 (P).
  - **Who exceeds 64.** The record's own run needs 17 graphs and E6 with its drift check needs 34. E7 uses 7–8 row counts, so 119–136 graphs.
  - **Test on torch 2.10** (the record's version, in the CPU venv). I mirrored the call pattern with E7's row counts (`scratch_cut/exp/recompile.py`). P = 32, 64 and 96 compiled 17 graphs each; P = 128 compiled 13. From P = 160 up, the full cycle (P = 256) included, 0 of 18 calls were compiled, and they stayed eager when called again after this "warmup". Dynamo logged `hit config.recompile_limit (64)`.
  - **Updates affected.** By the port's own `chain_rows`, the Cut updates whose chain runs eagerly, in whole or in part, number 86 of 91 (`ramp64_f30`), 71 (`ramp64_f60`), 85 (`ramp128_f30`) and 68 (`ramp128_f60`). For `cut_smoke` it is 10 of 13.
  - **Cost.** Eager `chain_chunk` writes out the `[512, 260, 4096]` float32 logits (2.2 GB) and makes about 10 elementwise passes over them, plus the unfused MLP and query blocks. That happens on each of the 288 calls per update. My estimate is +20–40% per affected update (unverified on a GPU; torch 2.13 not checked).
  - **Effect.** `e6.cut_k1`, the baseline, compiles fully. E7's success criterion is "equal loss at lower time", so the comparison is biased against E7, and the saving it looks for is at most a few percent at f = 0.3.
  - **Why the tests miss it.** The CPU checks disable Dynamo (`tests/method_checks.py:806`).
- fix: in `CutChain.__init__`, after `trainer_module('pr40')`, set `torch._dynamo.config.recompile_limit` (and `accumulated_recompile_limit`) to at least 17 × (row counts + 1), for example 256. Then either set `fail_on_recompile_limit_hit = True` or count `chain_chunk_eager`'s cache entries after the warmup and fail the job if any shape is missing. A CPU unit check can assert that 17 × (distinct `chain_rows` values + drift) does not exceed the limit.

### 2. [major] E7's time comparison can mix H100 and H200 without any flag
- where: `configs/e7/*.yaml`, `configs/e6/cut_*.yaml`, `configs/e1/cut_1m.yaml` (no `gpu:`); `loud/collect.py:10,103`; README (`gpu_worker_any.yaml # H100 or H200 (jobs without a gpu: requirement)`)
- evidence: `grep -rn '^gpu:' configs` returns nothing, so an any-GPU worker takes every Cut cell. E7's criterion is wall-clock against `e6.cut_k1`, which sits in another experiment. `collect.py` flags `GPU differs` only within one experiment, so an E7 cell on an H200 against a baseline on an H100 goes unflagged. Ledger round 1 #8 relies on configs pinning `gpu: H100`, but none does.
- fix: add `gpu: H100` to `e6.cut_k1` and the four E7 configs (and to E1's cell, whose wall-clock the plan reports). Alternatively, also flag a GPU mismatch against the cross-experiment baselines in `plots.BASELINES` and `collect.py`.

### 3. [minor] Turns swallows a collective mismatch when the part that finishes last has the extra `group_sum`
- where: `loud/cut.py:97-103`, `:60-74`
- evidence: `scratch_cut/exp/turns.py` runs part 0 with no collective and part 1 with one `group_sum`. `run()` returned normally, and part 1 received its own tensor, unsummed. `t.failed` held `RuntimeError('the parts of a sequence reached different collectives')`, but nothing raises it. The reverse case (part 0 holds the extra collective) does raise. So the check works in one direction only. The record's code is symmetric, so this is latent.
- fix: at the end of `run()`, `if self.failed is not None: raise self.failed`. Alternatively, raise in `group_sum` when another part is already `done`.

### 4. [minor] E7's plot and table never show its success criterion or its baseline
- where: `loud/plots.py:388-390` (`BASELINES` has no `e7`), `:346` (`e7_table` shows only H6's `credit_dump`)
- evidence: E7 is "equal loss at lower time against `e6.cut_k1`". `plot('e7')` draws only the four ramps' val losses (`final_plot`) and loss against sequences (`curves_plot`). It has no `train_seconds` and no `e6.cut_k1`.
- fix: add `'e7': ('e6', 'cut_k1')` to `BASELINES`, plus a table of val (and `val_loss_plain`) against `train_seconds` per ramp and for the baseline, as `e12_table` does.

### 5. [minor] `e1.cut_1m.s0` and `e6.cut_k1.s0` are the same 35-minute run
- where: `configs/e1/cut_1m.yaml`, `configs/e6/cut_k1.yaml`
- evidence: both run seed 0 on the 1M slice, unchanged, with checkpoints and `heldout_every: 10`. The only difference is `drift_every: 10`, which runs untimed with its own estimators and seed. Every draw goes through explicit generators, so it cannot change training. Nothing compares the two runs, so they are not used as a determinism check either.
- fix: run `e6.cut_k1` on seeds [1, 2] and read seed 0 from `e1.cut_1m`, adding `drift_every` there. Or keep both and add a `compare` job that makes them a determinism check.

### 6. [minor] The end merge is about a quarter of every 1M-slice run because it scores candidates rank by rank
- where: `loud/cut.py:259-276`
- evidence: the record's merge took 59.35 s on 8 GPUs (`log/result.json`). Here each of about 5,000 candidate scores runs 8 sequential batch-4 forwards, about 8 minutes by the README's own estimate. That is 8 of each 35-minute run, across roughly 25 Cut runs, all timed. One forward of 32 sequences per candidate would likely be several times faster (unverified). It changes only the bf16 rounding of close merge decisions, and no comparison relies on matching the record's merge choices.
- fix: an option, `merge_batch`, that scores the 32 rows in one batch. Keep the rank-by-rank layout as the default for verification runs only.

### 7. [minor, unverified] The bounds in `cut_prefix_match` (0.003 for 20 updates, 0.02 for 262) are not calibrated, yet every Cut cell gates on them
- where: `configs/verify/cut_prefix_match.yaml`; the `after` lists of `e1.cut_1m`, `e6.cut_*` and `e7.*`
- evidence: no measurement shows how far two runs that differ only in rounding drift apart over 262 updates. Those runs differ in the 8-way sum order and in torch 2.13 against 2.10; across versions, Inductor's kernels can flip bf16 roundings in the probes' logits. The maximum is taken over noisy per-step batch losses and spans the Boost → Cut switch. A spurious failure would block all 25 Cut cells.
- what would settle it: run `verify.cut_prefix` twice in the port, changing only the order of the 8-way sum in `CutChain.update` (for example, reversed ranks), and set both bounds from the per-step gap observed (with margin).

### 8. [nit] The drift check's `blend` duplicates `fast`
- where: `loud/cut.py:433,442`
- PR #40 sets `fast_weight = 1.0`, so `blend` is always identical to `fast`.

### 9. [nit] `end_merge` is duplicated
- where: `loud/cut.py:445-453` and `loud/proxy.py:174-184`
- The two methods are identical.

### 10. [nit] Each Cut estimator keeps about 76 MB after it measures
- where: `loud/cut.py:373-377`
- `estimator.measured` (chain, `g_top`, targets) is kept after `measure`, about 0.6 GB idle across the 8 ranks. Clear it with the capture stores.

### 11. [nit] `cut_windows` checks the windows' average numerically only with one GPU per sequence
- where: `tests/method_checks.py:884-931`
- The two halves meeting in `group_sum` are covered only by an index check. I ran the numeric check separately (`scratch_cut/exp/split_windows.py`): the mean of 4 windows equals the record's chain credits, relative error 1.7e-7. It is worth adding to the test.

## Checked and fine
- **CPU checks.** `cut_ranks` (1 m 36 s), `cut_windows` and `cut_run` all print `ok`. `tests/test_harness.py` passes (38 tests). A submission dry run of `configs/verify`, `e1`, `e6`, `e7` and `h6` validates, and the gates chain smoke → prefix → match → cells.
- **Virtual ranks** as `train_stages` builds them:
  - Capture seeded with `seed + 1000·sequence`, with rank = part; Boost and Cut generator `seed + 17 + 1000·sequence`. Both parts of a sequence draw the same bases.
  - Part = rank % split; the sequence slice is `rank_slice`'s.
  - Gradients are divided by valid tokens per rank, summed over 8 ranks in rank order, then divided by the 4 sequences. The loss is the mean over the 8 ranks (`average_ranks`).
  - The record's `SEED` is used only in `train_stages`, so replacing the seed by the job's covers every use.
- **Turns.**
  - Ordering: parts in order, the sum a + b written to every part's tensor.
  - Failure: a failing part wakes the other; an interrupt while waiting propagates; the `finally` waits for every part.
  - Thread-local state: grad mode (`estimate` is `@no_grad`), autocast (Capture's own context), device (always `cuda:0`), stream (default), and the deterministic flag (toggled only on the main thread, outside `run`).
  - Inductor compiling first on the pool thread works (CPU test).
  - Inductor and Dynamo call `signal.signal` only in the compile-worker subprocess.
  - The custom op `routed_response` traces without a graph break.
- **Schedule.**
  - `stage_schedule(steps × batch)` gives 1,212 updates with 242 Boost on 10M, and 114 with 23 on 1M.
  - The horizons are per phase.
  - The switch builds a new optimizer with the phase horizon and calls `handoff_optimizer` (state carried over, `t = phase_step − 1`); `set_rate` runs after the switch.
  - At `38m`, `record_settings` equals the record's defaults and `main()`'s chunk arguments.
- **End merge.**
  - `virtual_holdout_loss` reproduces each rank's single batch of 4 and the float64 sum.
  - `curvature_bases` at rank 0, world 1 equals the record's rank 0.
  - `joint_parts` and `end_merge` look `holdout_loss` up by module global, so the patch reaches them.
  - The means follow the record's rule: first sequence at or past 0.6, every 5 updates and at the last; float32 lerp.
  - The merge is timed; the plain weights are saved first and scored untimed as `val_loss_plain`.
- **E6.**
  - Window `(s mod K)·rows`, cycle `s // K`.
  - The bases are drawn on every update (the stream is unchanged), and the cycle's first draw is held per site.
  - Unbiased through the random column signs.
  - Part 0 takes the first half of each token's window, part 1 the second.
  - `rows: 512` maps to `None`, which runs the record's `chain_credits` itself (asserted by `cut_windows`).
  - Drift check: its own seed and estimators, the full cycle on a held-out sequence, untimed, with no effect on training draws.
- **E7.**
  - The ramp starts at the first Cut update (documented) and is quantized down to multiples of 64.
  - Tiled windows `(t·rows) mod 512` read every row in every update.
  - Unbiased for any window.
- **Data.** The 10M split matches the record's: `randperm(4880, seed 1)`, the last 32 held out, the archived rows' hash checked.
- **Benchmark rules.** No `val.pt` read in a run; held-out sequences feed no update; no choice on validation.
- **The new hooks** in `loud/train.py`. No other trainer defines `warmup`. The proxy's `finish` is `None` unless `end_merge`, so other tasks' results are unchanged.
- **Memory.** The record's per-GPU peak is 17.5 GB. Here one part peaks while the other holds its state from the last handoff, about 20 GB, which fits in 80 GB (reasoned, not measured).
- **Time.** The estimates are 8 × the published per-GPU times (Boost 0.196 s, Cut 2.055 s per update), as the README states. Seeds are as the plan asks: E6 three, E7 two, sharing seeds 0 and 1 with `cut_k1`.
